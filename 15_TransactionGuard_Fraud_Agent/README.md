# 🚨 TransactionGuard — Adaptive Fraud Investigation Agent

> A **LangGraph** agent that investigates digital-wallet transactions for fraud the way a human analyst would — forming a hypothesis, deciding **which check to run next**, deciding **when it has enough evidence to stop**, and checking its own memory of similar past cases before delivering an explainable verdict. Not a fixed pipeline with an LLM narrating the result at the end.

**Portfolio Project 15** · Fintech / payments domain — fraud detection, adaptive agentic reasoning, episodic memory (RAG).

## ❓ What is this? (in plain English)

**The business problem.** Digital wallets (think Keenu, EasyPaisa-style apps) process huge volumes of transactions, and some of them are fraud: an account gets taken over and drained in a burst of rapid transfers, a compromised device suddenly spends far above the account's normal pattern, or a transaction shows up from a location the account has never touched. A wallet operator needs to catch these **fast** — but a bare "risk score" isn't good enough. A compliance team can't act on a number with no reason, and a customer can't be told "our AI blocked you" with no explanation.

**Most fraud systems get this half right.** They run a fixed checklist of rules on every transaction and hand back an opaque score — automation, not judgment. There's no adapting to what's actually unusual about *this* transaction, and no memory of what happened with similar cases before.

**The solution TransactionGuard demonstrates.** An agent that reasons like an analyst instead of running a checklist:

1. It looks at a transaction and forms a **hypothesis** about what might be wrong.
2. It picks **one check to run first** — the one most likely to confirm or refute that hypothesis — not all of them blindly.
3. After each check, it decides: *do I have enough evidence, or should I investigate further?* This is a real conditional loop, capped at one pass per check so it can never spin forever.
4. It searches its own memory (a vector database of past investigations) for a similar case and factors in what happened then.
5. It delivers a **risk level, a recommended action, and a plain-English explanation** citing exactly which signal(s) drove the decision.

**Why this is genuinely agentic, not just "call an LLM."** A pipeline that always runs every check and has an LLM summarize the result at the end isn't reasoning — it's a narrator bolted onto a script. Here, the number of checks run and their order is a per-transaction decision the agent itself makes, and its memory of prior cases actually improves over time as an analyst confirms or corrects its verdicts.

**No real financial data is involved.** There's no real wallet transaction data available for a portfolio project, so the entire dataset — 50 mock accounts, ~1,700 transactions, with a deliberate mix of normal behavior and injected anomalies (velocity bursts, amount spikes, geo jumps, new devices) — is generated by a synthetic-data script and clearly labeled as such. The labels are used only to *evaluate* the agent's accuracy afterward; the agent itself never sees them.

## 🧠 How it works — the reasoning graph

```
                    ┌────────────────────┐
                    │  ingest_transaction  │
                    └──────────┬─────────┘
                               │
                    ┌──────────▼─────────┐
                    │  triage_hypothesis   │  ← LLM: forms a hypothesis,
                    │                       │    picks the first check to run
                    └──────────┬─────────┘
                               │
              ┌────────────────▼────────────────┐
              │            run_check              │  ← velocity | amount_threshold |
              │   (whichever check was chosen)     │    geo_anomaly | device_fingerprint
              └────────────────┬────────────────┘
                               │
                    ┌──────────▼─────────┐
              ┌────►│  evaluate_evidence   │  ← LLM: enough evidence, or
              │     │                       │    run one more check?
              │     └──────────┬─────────┘
              │      not enough │  enough
              └─────────────────┘         │
                                          ▼
                              ┌──────────────────────┐
                              │   retrieve_precedent   │  ← pgvector similarity
                              │                         │    search over past cases
                              └──────────┬───────────┘
                                         │
                              ┌──────────▼───────────┐
                              │     final_verdict       │  ← LLM: risk level,
                              │                         │    action, explanation
                              └──────────┬───────────┘
                                         │
                              ┌──────────▼───────────┐
                              │  store_episodic_memory  │  ← embed + store this
                              │                         │    case as a new precedent
                              └────────────────────────┘
```

**The loop is the point.** `evaluate_evidence` can send the graph back to `run_check` for another signal, or forward to `retrieve_precedent` — a real branch decided per-transaction, hard-capped at one pass per check (4 checks exist, so at most 4 iterations, guaranteeing termination regardless of what the LLM decides).

**Architecture:**

```
                    ┌──────────────────────────────────────┐
                    │   FastAPI backend (async, WebSocket)    │
                    │   202 Accepted → background task runs   │
                    │   the graph → result pushed live         │
                    └───────┬──────────────────────┬────────┘
                            │                       │
              ┌─────────────▼──────────┐  ┌────────▼─────────────┐
              │  Postgres + pgvector      │  │       Redis            │
              │  accounts · transactions   │  │  BYOK demo-key rate    │
              │  investigations · precedents│  │  limit · history cache│
              └────────────────────────┘  └───────────────────────┘
                            ▲
                            │
                    ┌───────┴────────────┐
                    │  Next.js frontend    │
                    │  live console · feed  │
                    │  · ops dashboard       │
                    └────────────────────┘
```

**BYOK (bring your own key).** Every OpenAI/LLM call is made with either the visitor's own API key (pasted client-side, sent per-request, never logged or persisted server-side) or a tightly rate-limited shared demo key — never a personal always-on key sitting in the backend's `.env`.

**The human-in-the-loop.** An analyst logs into `/ops`, reviews any completed investigation's full reasoning trail, and clicks **Confirm fraud** or **Mark false positive**. That feedback rewrites the stored precedent, so a wrong verdict doesn't stay wrong forever in the agent's memory.

## ⚙️ Run it yourself

**Prerequisites:** Python 3.11+, Node 18+, Docker Desktop (for local Postgres+pgvector/Redis, or point at your own Supabase/Upstash), an OpenAI API key.

```bash
# 0. Env
cp .env.example .env          # fill in ANALYST_PASSWORD, JWT_SECRET, etc.

# 1. Local Postgres (pgvector) + Redis
docker compose up -d          # auto-creates the schema from db/schema.sql

# 2. Backend (installs the agent's deps too — self-sufficient)
pip install -r backend/requirements.txt
python data/generate_synthetic_data.py   # generates accounts.json / transactions.json
python data/seed_db.py                   # seeds Postgres
cd backend && uvicorn main:app --port 8020 --reload

# 3. Frontend
cd frontend && npm install && npm run dev      # http://localhost:3000
```

Full step-by-step notes: [`RUN_LOCALLY.txt`](RUN_LOCALLY.txt).

## 🧩 Tech stack

| Layer | Technology |
|-------|-----------|
| Agent framework | **LangGraph** — conditional/looping edges, hard-capped iteration |
| LLM | **OpenAI GPT-4o** (triage · evidence evaluation · final verdict) + `text-embedding-3-small` |
| Memory / RAG | **Postgres + pgvector** — episodic precedent storage & cosine-similarity retrieval |
| Backend | **FastAPI**, `asyncpg`, **Redis** (BYOK demo-key rate limiting + transaction-history cache), WebSockets (202 Accepted → live push) |
| Auth | **JWT** (`python-jose`) — analyst ops-dashboard login, `bcrypt` password hashing |
| Frontend | **Next.js**, TypeScript, Tailwind, `framer-motion`, dark/light theme toggle |
| Data | Synthetic transaction generator — 50 accounts, ~1,700 transactions, labeled injected anomalies |
| Deployment | Render (backend) + Vercel (frontend) + Supabase (Postgres/pgvector) + Upstash (Redis) |
